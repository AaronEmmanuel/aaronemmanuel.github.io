How the project developed

Start with a working robot.
Then give it eyes and words.

01

Build a dependable baseline

First, make the arm pick and place.

I built the workcell and a scripted controller so the gripper had to lift real simulated objects through contact. That gave the project a working reference before adding AI.

02

Learn from an approach that failed

Copying movements was not enough.

A model trained to imitate demonstrations struggled to complete tasks. I kept those failed experiments and changed direction: a learned model now helps calculate robot movement, while feedback checks the arm’s progress.

03

Connect language to what the camera sees

Ask for a part. Check the answer.

A vision-language model sees the camera image and request together. Separate checks verify its proposed target, and depth sensing estimates where to grasp. Missing or ambiguous parts lead to clarification.

04

Handle the moments that go wrong

Success needs more than reaching the tray.

The software checks the grasp and placement, allows one retry after a missed grasp, and stops when the target moves or feedback fails. Testing exposed waiting and timing problems that shaped the final controller.

The project connects an everyday request to a visible, checked robot action. It demonstrates the engineering behind an AI-enabled workcell, from a conventional baseline to camera-guided manipulation.

What still needs work

The scene has three known parts, two fixed trays and a calibrated camera. Arbitrary objects, clutter and a physical robot need further development and testing. The simulation runs slower than real time, and its Stop button is not a hardware emergency stop.

My contribution

I developed the workcell, control, perception, learning pipeline, ROS interfaces and evaluation with AI-assisted coding. The Panda robot assets come from Google DeepMind’s MuJoCo Menagerie; Qwen provides the pretrained vision-language model.

A closer look at the engineering Expand for architecture, testing and limitations ↓

Who does what

Qwen3-VL receives the request and a numbered RGB image. Colour, geometry and image-space checks validate its proposed target. Calibrated RGB-D estimates the grasp pose. A PyTorch model predicts a 6-by-7 robot Jacobian, which conventional feedback uses to calculate joint movement. Task phases and gripper sequencing remain engineered; this is not an end-to-end visual action policy.

Learning and evaluation

Sixty scripted expert episodes supplied the initial imitation data. Action cloning completed 0/18 tasks; corrective cloning also reached 0/18, and recovery-augmented cloning reached 6/18. The replacement Jacobian model used 60,000 synthetic kinematics samples and 12,000 validation samples. The final continuous protocol completed 10/10 placements and passed 15/15 planned checks. It is separate from the original 14/15 protocol. All 163 automated Ubuntu tests passed at that release.

On the final visual attempts, the model itself abstained or proposed an independently valid target on 12/15 attempts. Guards rejected three incorrect negative-case proposals. Guarded refusal does not mean the model itself recognized that it should abstain.

Continuous supervision

A separate ROS 2 server advances MuJoCo physics and publishes stamped camera and joint feedback. The controller checks freshness, contact, progress and command deadlines. Stationary sensing enters explicit supervised Hold; movement reactivates the motion deadline. Cancellation retains the gripper command and pauses simulated physics. Reset discards feedback from the previous scene.

Current operating limits

Two new continuous-mode operator recording attempts on October 11 stopped before visual selection because a command deadline expired. They are retained as development failures and do not change the earlier test results. The language walkthrough therefore uses the existing stepped mode, with physics paused between requests. Public live hosting requires further runtime qualification.

Historical paired stepped experiments reduced median fresh-image inference from 34.26 to 4.80 seconds and a separate complete task from 131.29 to 74.06 seconds. These measurements are not a speed claim for the continuous runtime. Rendering shares the simulator executor, and requested update rates are not real-time hardware guarantees.
